# App Store 출시 방법론 — 엔진 전환 검토와 계획

상태: **제안 문서. 코드·배포 변경 없음.** 작성 2026-10-12, 기준 커밋 `dfcb826` (v0.19.29).
작성 Claude, 검토 Codex (Orca 터미널 세션 `01a11fd7`, 2026-10-12). 두 에이전트가 합의한 내용과 사용자 결정이 필요한 항목을 구분해 적는다.

## 1. 결론

- 엔진 후보 1순위는 **Unity(C#, IL2CPP)**, 2순위는 Godot 4. 웹뷰 래핑(Capacitor 등)은 사용자 입장의 사용성 때문에 제외한다.
- **전면 이식을 바로 시작하지 않는다.** 먼저 트랙 1개·기체 1개 규모의 **검증 스파이크**를 Unity로 만들어 실제 iPhone에서 웹 빌드와 같은 절차로 비교한다. 합격 기준(5절)을 넘으면 본 이식, 차이가 불분명하면 보류한다.
- 발열 개선은 **가설**이다. 엔진 전환만으로 보장되지 않으며 수치 기대값을 미리 적지 않는다. 측정으로 확인한다.

## 2. 왜 재작성인가

현재 스택은 바닐라 TypeScript + Three.js 0.184 + Vite, 약 17k줄(TS 15.5k, CSS 1.6k), 테스트 73파일. 이미 PWA로 설치·오프라인·업데이트를 지원한다.

레이싱 게임의 모바일 UX는 프레임 페이싱, 입력 지연, 햅틱, 오디오 지연, 파티클·후처리 품질이 결정한다. 전부 엔진 영역이고 WKWebView 안에서는 천장이 낮다. 따라서 "UI 프레임워크"가 아니라 "게임 엔진"을 고르는 문제다.

| 후보 | 판단 | 이유 |
| --- | --- | --- |
| Unity | **1순위** | 모바일 3D에서 가장 검증됨. iOS/Android 동시 빌드, Metal 직접 호출, ASTC, Adaptive Performance(열 상태 API), LOD·오클루전, 프로파일러, IAP·Game Center SDK. 런타임 요금은 2024년 9월 철회. |
| Godot 4 | 2순위 | 오픈소스. Unity가 싫을 때 대안. 모바일 3D 렌더러와 생태계가 아직 얇다. |
| Capacitor | 제외 | 기존 빌드 그대로 가장 빠르게 심사에 올릴 수 있으나 사용자가 사용성 문제로 제외. |
| React Native + expo-gl | 제외 | 코드 재사용률은 가장 높지만 주행 UX·발열이 개선되지 않음. 아래 참고. |
| Flutter | 제외 | 3D 사실상 없음. |
| SwiftUI + RealityKit | 제외 | 네이티브 UX는 최고지만 iOS 전용, 게임 툴링 약함. |

React Native + `expo-gl`(+ `expo-three`)를 제외한 이유. `expo-gl`은 네이티브 GL 컨텍스트를 WebGL 모양의 API로 JS에 노출하므로 Three.js 레이스 코드를 거의 그대로 가져가고, 메뉴·격납고·상점만 네이티브 뷰로 다시 짜면 된다. 햅틱·IAP·앱 복귀는 Expo 모듈로 붙는다. 그러나:

- 렌더링 경로가 같다. iOS에서 JS → GL 호출 → ANGLE → Metal이라 브라우저 WebGL과 본질이 같고, 드로우콜마다 JS가 호출하는 오버헤드도 그대로다.
- 물리·NPC 루프는 오히려 느려질 수 있다. React Native 기본 엔진 Hermes는 JIT 없는 바이트코드 인터프리터라 Safari JIT보다 수치 계산이 느리다.
- 열 상태 API, ASTC, LOD·오클루전, 프레임 페이싱 같은 엔진 도구가 없다. 발열은 지금과 같거나 나쁘다.
- `expo-three`는 8.0.0 이후 활동이 뜸하고 열린 이슈가 100개 넘는다. README가 시뮬레이터 비지원과 Metro 번들러 우회법을 명시한다. `@react-three/native`도 내부는 같은 `expo-gl`이다.

"메뉴를 네이티브 느낌으로, 레이스는 지금 수준 유지, 코드 최대 재사용"이 목표라면 Capacitor보다 나은 길이다. 이 문서의 목표인 주행감·프레임·발열 개선에는 엔진 전환이 필요하다.

### 플랫폼 범위

Unity는 iOS/Android 외에 데스크톱과 웹 빌드도 지원한다. 하지만 세 묶음의 비용이 다르다.

| 플랫폼 | 따라오는가 | 비용 |
| --- | --- | --- |
| iOS / Android | 주 타깃 | 이 문서의 본 작업 |
| macOS / Windows | 거의 그대로 | 같은 코드·씬에 빌드 대상만 추가. 키보드·게임패드 입력(Input System), 창 크기·해상도, UI 스케일 정도. 스토어 연동은 별도 |
| 웹(Unity Web) | 빌드는 되지만 품질이 다름 | 아래 참고 |

Unity 웹 빌드의 제약:

- 용량과 로딩. 3D 게임의 Unity 웹 빌드는 압축해도 수십 MB다. 현재 Vite 번들은 수 MB 수준이라 첫 로딩이 몇 배 느려진다.
- 성능. WebAssembly + WebGL2 경로라 이 문서가 벗어나려는 ANGLE 계층을 다시 타고, 그 위에 Unity 런타임 오버헤드가 얹힌다. 모바일 브라우저에서는 현재 Three.js 버전보다 느릴 가능성이 크다. 멀티스레드 Jobs는 웹에서 기본 꺼져 있다. 모바일 브라우저 공식 지원은 Unity 6부터다.
- PWA 흐름. 현재의 설치·오프라인·업데이트 적용 흐름([웹앱 문서](WEB_APP.md))은 Unity 웹 템플릿 위에 다시 만들어야 한다.

방침: iOS/Android가 주 타깃이고 데스크톱 독립 실행 빌드는 덤으로 가져간다. 웹은 데스크톱 브라우저용 데모 수준으로 본다. 현재 웹 사이트를 Unity 웹 빌드로 대체할지는 본 이식 뒤에 로딩 시간과 5절 기준을 같은 절차로 재서 따로 결정한다. 그때까지 현재 웹은 8절대로 계속 운영한다.

## 3. 발열·성능에 대한 판단

열의 원천은 "GPU가 그리는 픽셀 × 셰이더 비용"과 "CPU가 매 프레임 하는 일"이다. Unity는 그 위의 오버헤드를 걷어내고 조절 도구를 줄 뿐이다.

줄어들 가능성이 있는 것:

- 번역 계층. 현재 경로는 JS → WebGL2 → ANGLE → Metal이고, Unity는 Metal 직접 호출이라 드로우콜당 CPU 비용이 낮다.
- 브라우저 비용. WKWebView 프로세스, JS 엔진, WebGL 캔버스 위에 CSS HUD를 합성하는 컴포지터.
- JIT. IL2CPP AOT 빌드가 JIT JS보다 전력 효율이 좋고, 물리·NPC 루프는 Burst/Jobs로 더 줄일 수 있다.
- 압축 텍스처(ASTC) 기본 지원. 메모리 대역폭이 열의 큰 몫이다.
- 열 상태를 읽을 수 있다. Adaptive Performance가 iOS 열 상태를 받아 해상도·프레임을 낮춘다. 웹에서는 OS가 조용히 스로틀링할 뿐이다.

그대로인 것:

- 같은 해상도로 같은 셰이더를 60fps로 그리면 GPU는 같은 일을 한다. 오버드로우, 블룸, 그림자, 파티클 수는 엔진이 대신 줄여주지 않는다.
- 현재의 `RenderQuality` 3단계, 픽셀 비율 상한 1.75, 인스턴싱 같은 대책은 Unity에서도 똑같이 해야 한다. 하기 쉬워질 뿐 사라지지 않는다.

합의: Claude가 처음 제시한 "동일 콘텐츠 기준 20~40% 전력 감소"는 근거 없는 추정이라 **기대 효과 수치로 적지 않는다.** 개선을 주장하려면 5절의 반복 측정에서 확인해야 한다.

## 4. 검증 스파이크

목표: "Unity로 가면 실제로 좋아지는가"를 실기기에서 같은 절차로 비교한다. 2~4주는 이 범위의 **시간 상자**이며 완성도 동등 구현을 보장하는 일정이 아니다.

코스와 기체: **48번 SURFACE RUSH + 기본 Vanguard, 보통 난이도.** 현재 레시피에 코너, 반경 130m 수직 루프, 2회전 헬릭스, 좌우 분기, 점프가 모두 있다.

포함:

- 터치 조향·고도·브레이크·부스트
- 충돌·니어미스·드리프트
- 분기 선택, 점프 슬로모션과 카메라 1종
- 경쟁 NPC
- 최소 HUD, 소리·진동
- 일시정지·백그라운드 복귀, 설정·기록 저장
- 마린 배경·블룸·투명 효과를 웹과 비교 가능한 수준으로

제외: 전체 캠페인, 상점, 튜토리얼, 전체 아이템, 패링, 각성, 공유, 결제, 다른 기체. **비교할 웹 빌드에서도 같은 기능을 비활성화한다.**

스파이크의 트랙 지오메트리는 7절대로 웹 생성기에서 구워 내보낸다. 생성기 포팅은 본 이식에서 한다.

## 5. 합격 기준 (제안값)

측정 절차는 [자동 품질 문서](AUTOMATIC_QUALITY.md)의 트랙별 기준선 절차를 그대로 쓴다. 냉간/10분, 3회 반복, 4초 창. 양쪽 빌드에서 해상도·밝기·NPC 수·날씨·효과·입력 시퀀스를 고정한다. 최소 지원 후보 iPhone과 최근 iPhone에서 각각 측정하고, 양쪽 모두 60fps 목표에 대응하는 `balanced` 품질을 주 판정으로 삼는다.

| 항목 | 기준 |
| --- | --- |
| 프레임 | 평균 ≤17.5ms, 전체 p95 ≤20ms, 최악 4초 창 p95 ≤25ms |
| 지속 성능 | 마지막 2분 평균 프레임 시간이 초기 안정 구간보다 10% 넘게 악화되지 않음 |
| 열 상태 | 10분간 nominal/fair 유지, serious/critical 진입 없음 |
| 입력 지연 | 외부 고속 촬영 50회 이상, 터치→보이는 반응 p95 ≤80ms, 웹보다 10ms 넘게 악화되지 않음 |
| 전력 | 동일 조건에서 웹 대비 악화 없음. 개선을 주장하려면 반복 측정에서 약 20% 이상 감소 확인 |

추가 규칙:

- 기존 측정기가 제외하는 **250ms 초과 멈춤은 별도 집계**한다.
- 배터리 잔량 10분 차이는 보조 지표다. 그것만으로 판정하지 않는다.
- 전력·열 상태는 양쪽 모두 같은 Instruments 절차로 본다. [Apple Power Profiler](https://developer.apple.com/documentation/xcode/measuring-your-app-s-power-use-with-power-profiler)
- 웹 빌드의 프레임은 Safari 원격 디버깅과 `[race-performance]` 콘솔 보고로, Unity 빌드는 Profiler와 같은 창 크기의 자체 측정기로 기록한다.

판정: **필수 기준을 모두 통과하고**, 웹이 실패한 지속 성능·입력 문제를 해결하거나 유의미한 전력 개선을 보이면 Unity를 채택한다. 둘 다 이미 쾌적하고 개선이 불분명하면 전면 이식은 보류한다.

## 6. 로직 포팅 계획

### 포팅 순서

1. 기초 데이터·계산: `droneCatalog`, `droneConfiguration`, `difficulty`, `raceChallenge`, `altitudeProfile`, `flightDynamics`
2. 트랙 질의와 주행: `Track.sample` 계약 → `createDrivingModel` → `raceProgress`, `raceScoring`, `drift`, `jumpPassage`
3. 세션: `createTimeAttack`, `createRaceSession`, `aiRoster`, `finishCoast`, `raceResultData`
4. 본 이식: `parry`, `supportMissile`, `awakening`, 진행·장착·보상 규칙, 고스트·튜토리얼
5. 플랫폼 독립 모듈: `automaticQuality`, `touchInput`, `gamepadInput`의 상태 해석

스파이크는 1~3단계 중 SURFACE RUSH 주행에 필요한 부분만 옮긴다.

### 브라우저 결합 분리

`src/game`·`src/platform`에서 `document`, `window`, `localStorage`, `navigator`, `requestAnimationFrame`, `performance.now`를 직접 쓰는 파일은 20개다. 대표 처리:

- `createTrack` → 데이터 / 샘플러 / 메시 생성으로 분리
- `createRace` → 시뮬레이션 진행 / 화면 연결로 분리
- `createTouchControls`의 DOM 입력 → Unity 입력 어댑터로 교체
- `progressStore`의 IndexedDB·localStorage·BroadcastChannel → 저장 인터페이스 밖으로
- `progress`·`campaign` → 저장소 접근과 `Date.now()` 분리
- `arcRail`은 DOM 모듈이 아니다. 트랙 샘플러·분기 모듈을 통해 Three 수학에 간접 결합돼 있을 뿐이다.

원칙: 시간·난수·저장·입력·효과 출력은 모두 주입한다.

### 테스트 이전

기존 `tests/*.test.mjs`에서 **초기 상태 + 트랙 revision + 난수열 + dt별 입력 + 기대 상태/이벤트**를 JSON으로 추출해 C# 테스트가 읽는다. 정수·이벤트·분기 ID는 정확 일치, 실수는 명시한 허용오차로 비교한다. 골든 데이터와 별도로 직교 프레임, 연속성, 분기 접촉 0 같은 불변조건 테스트도 유지한다. 주행 계산은 우선 double을 유지하고 렌더링 경계에서 float로 변환한다.

## 7. 트랙 지오메트리

현재 기체와 도로는 모델 파일이 아니라 Three.js 코드로 생성한다. 트랙은 화면용 메시일 뿐 아니라 **기체 자세와 분기 판정에도 쓰인다.** 루프·헬릭스는 `TrackFrame`의 tangent/right/up으로 자세를 정하고, 분기 선택은 offset/고도와 결정 구간을, 이동 거리는 경로별 `distanceScale`을 쓴다. 렌더링 메시와 주행 경로가 어긋나면 판정도 틀어진다.

- 스파이크: 웹 생성기로 **메시 + 주행 데이터**(경로별 위치·자세·곡률·`section`·`distanceScale`, 분기 경계·장애물·점프 구간)를 함께 구워 내보낸다. glTF만으로는 부족하다.
- 본 이식: 생성기를 C#으로 포팅하고 **에디터에서 미리 굽는 방식**을 쓴다.

## 8. 분담과 웹 운영

- Claude: Unity 씬, 셰이더, VFX, 카메라 연출, UI(UI Toolkit)
- Codex: C# 규칙·주행 물리, 데이터 변환 도구, 에디터 자동화, 테스트, 성능 측정
- 공동 확정 계약: `TrackFrame`, `DrivingState`, 효과 이벤트
- 섞인 항목은 기존 규칙대로 로직(Codex) 먼저, 보이는 부분(Claude) 다음

웹은 계속 서비스한다. 스파이크 동안 **신규 기능은 동결**하고 심각한 버그·운영 수정만 받는다. 비교 기준 커밋과 데이터 revision은 고정하고, 그 사이 수정은 별도 이식 목록으로 관리한다.

사용자 역할: Unity 에디터 기본 조작, 기기 빌드·TestFlight 흐름. Apple Developer Program 가입과 서명 설정은 에이전트가 대신할 수 없다.

## 9. 단계

### Phase 0 — 기준선

- 웹 빌드로 5절 절차를 먼저 수행해 기준선 표를 채운다. 이 표는 아직 비어 있다.
- 완료 기준: 두 iPhone × SURFACE RUSH × 냉간/10분 × 3회 기록.
- 리스크: 기준선 없이 스파이크를 시작하면 비교가 불가능하다.

### Phase 1 — 스파이크

- 4절 범위를 Unity로 구현. 7절대로 웹에서 구운 트랙 데이터 사용.
- 완료 기준: 실기기에서 5절 측정 완료, 판정 기록.
- 리스크: 주행감 재현 실패. 골든 데이터 비교로 조기에 드러나게 한다.

### Phase 2 — 결정

- 채택 / 보류 / 중단을 사용자가 결정한다. 보류면 웹 동결 해제.

### Phase 3 — 본 이식 (채택 시)

- 6절 순서대로 로직 포팅, 생성기 C# 포팅, 전체 트랙·기체·UI·상점·캠페인.
- 완료 기준: 현재 웹 기능 동등, 골든 테스트 전부 통과, 두 iPhone에서 5절 기준 통과.
- 리스크: 기간. Codex 추정은 Unity 경험자 1명 전업 기준 4~8개월, 학습 병행 시 6~12개월 이상. 견적이 아니라 규모 추정이다.

### Phase 4 — 출시 준비

- Apple Developer Program, 번들 ID, 서명, 개인정보 매니페스트, 스크린샷·설명, TestFlight 외부 테스트.
- 결제·Game Center는 범위 밖. 필요하면 별도 결정.

## 10. 리스크

- 스파이크 결과가 "둘 다 쾌적"으로 나올 수 있다. 그때는 이식 근거가 없다. 이 경우를 실패가 아니라 정상 결과로 취급한다.
- 트랙 생성기 포팅이 가장 크고 불확실하다. 7절의 "구워서 내보내기"로 스파이크에서 분리한다.
- 웹 동결이 길어지면 두 코드베이스가 벌어진다. 동결 기간을 스파이크 시간 상자로 제한한다.
- 사용자의 Unity 경험이 없다. 에디터 작업을 코드로 자동화하는 비중을 높여 의존을 줄인다.

## 11. 사용자 결정 필요

- 스파이크 시작 여부와 시작 시점
- 최소 지원 iPhone 기종
- 스파이크 동안 웹 신규 기능 동결 수용 여부
- Unity 라이선스 플랜(Personal 무료 한도 확인)과 Apple Developer Program 가입
