# 이용 분석과 로그인 도입 순서

로그인·클라우드 저장에 앞서 GA4로 방문 → 주행 시작 → 완주 → 재도전·재방문을 측정한다. 기존 IndexedDB의 게임 기록·포인트·구매 저장은 그대로 사용하며, 분석 성공 여부와 분리한다.

## 사용자가 준비할 것

현재 진행 방식은 **Codex의 관리용 MCP로 속성·스트림·맞춤 정의를 설정**하는 것이다. [관리 API 연결 안내](ANALYTICS_ADMIN_SETUP.md)에 인증과 연결 현황을 정리했다. 2026-10-07 사용자 인증 후 기존 개인 계정 이름을 `summerz.net`으로 변경하고 Speedracer 속성·웹 스트림·맞춤 정의를 생성했다. 측정 ID `G-86SQDL5ZDS`를 배포 저장소의 Actions 변수에 등록했다. 분석 코드 배포와 실제 게임 이벤트 수신 확인은 아직 남아 있다.

직접 설정하려면 아래 절차를 사용할 수 있다.

1. [Google Analytics](https://analytics.google.com/)에서 계정과 **GA4 속성**을 만든다. 보고 시간대는 대한민국, 사이트 이름은 Speedracer로 설정한다.
2. 관리 → 데이터 스트림 → 웹에서 **`https://speedracer.summerz.net`**을 등록한다.
3. 웹 스트림의 **측정 ID(`G-…`)**를 전달한다. 비밀번호·API 키·서비스 계정 파일은 필요 없다. 측정 ID는 공개 설정값이다.
4. 향상된 측정의 **페이지 조회 → 고급 설정 → 브라우저 기록 이벤트 기반 페이지 변경**을 끈다. 화면 이동은 코드에서 직접 전송하므로 자동 기록과 겹치면 중복된다. 다른 자동 측정도 우선 꺼두고 필요한 항목만 추가한다.
5. Google Signals와 광고 개인화는 활성화하지 않는다. 방문·주행 분석만 사용한다.
6. 관리 → 맞춤 정의에서 아래 이벤트 매개변수를 등록한다. 등록 후 보고서 반영까지 시간이 걸릴 수 있다.

| 이벤트 범위 맞춤 측정기준 | 매개변수 |
| --- | --- |
| 화면 | `screen_name` |
| 트랙 | `track_id` |
| 경기 방식 | `race_mode` |
| 난이도 | `difficulty` |
| 기체 | `ship_id` |
| 조작 분류 | `control_type` |
| 앱 버전 | `app_version` |
| 설치 앱 / 브라우저 | `app_mode` |
| 경기 결과 | `result` |
| 중도 종료 이유 | `quit_reason` |

충돌·이탈·통과 횟수와 주행 시간·별점은 필요할 때 이벤트 범위 **맞춤 측정항목**으로 `collisions`, `off_track_exits`, `obstacles_passed`, `elapsed_seconds`, `stars`를 등록한다. 주행 시간의 단위는 초, 나머지는 표준 숫자다. 기기·운영체제·브라우저는 GA4 기본 보고서도 함께 본다. `control_type`은 터치 입력 가능 기기/데스크톱 분류이며 실제 매 순간의 입력 장치를 추적하지 않는다.

## 배포 연결

실제 **빌드를 수행하는 배포 저장소**의 Settings → Secrets and variables → Actions → Variables에 `GA_MEASUREMENT_ID`를 추가한다. 현재 서비스 저장소는 `summerz/speedracer-site`이며 소스 저장소 `summerz/speedracer`의 변수는 자동 공유되지 않는다. 배포에 사용하는 저장소에 워크플로 변경과 변수가 함께 있어야 한다.

`.github/workflows/pages.yml`이 이 변수를 `VITE_GA_MEASUREMENT_ID`로 전달한다. 변수가 비어 있으면 분석과 동의 안내 모두 꺼진다. 변경 후에는 다시 빌드·배포해야 한다. PWA에는 기존 파일 내용 해시 기반 업데이트가 적용된다.

로컬 설정 예시는 `.env.example`에 있다. **개발 서버·로컬 배포 미리보기에서는 ID가 있어도 전송하지 않는다.** 배포 빌드이며 호스트가 `speedracer.summerz.net`일 때만 활성화한다.

## 동의와 데이터 범위

- 측정 ID가 설정된 서비스의 첫 메뉴 화면에서 선택 안내를 제공한다. 동의 전에는 Google 태그도 불러오지 않는다. 거절해도 모든 게임 기능을 사용할 수 있다.
- 공통 헤더의 **이용 분석**에서 선택을 변경한다. 선택은 기기 브라우저에 저장하며 주행 화면에는 안내를 표시하지 않는다.
- 동의 후 GA4가 쿠키와 기기 정보를 이용해 방문·재방문을 측정한다. 광고 저장·광고 사용자 데이터·광고 개인화는 거부로 설정하고 Google Signals도 끈다.
- 해제하면 이후 이벤트 전송을 중단하고 GA 쿠키를 삭제한다. 이미 전송된 데이터의 삭제까지 수행하는 기능은 아니다.
- 이름·이메일·게임 저장 파일·잔액·구매 내역·임의 입력값·경기별 UUID는 보내지 않는다. 화면 URL은 고정 경로만 보내며 쿼리는 제외한다. 초기 참조 URL은 출처(origin)만 전달한다.
- 거절한 이용자·차단된 태그·오프라인 경기는 잡히지 않는다. GA 수치는 전체 이용자 수나 보상·기록의 원장이 아니다. 동의 전 기록은 소급 전송하지 않는다.

## 이벤트

| 이벤트 | 시점 | 주요 값 |
| --- | --- | --- |
| `page_view` | 격납고·캠페인·상점·레이스 화면 진입 | 화면, 고정 URL |
| `level_start` | 시작 카운트다운 진입 | `level_name`, 트랙·방식·난이도·기체·조작 분류, `is_retry` |
| `level_end` | 완주 또는 제한시간 실격 | 통과 여부, 결과, 주행 시간·완료 랩·충돌·이탈·장애물 통과·순위·별점 |
| `race_quit` | 완주 전 재시작·화면 이탈·페이지 종료·렌더러 오류로 이탈 | 종료 이유, 종료 전 집계 |

모든 이벤트에 `app_version`, `app_mode`를 붙인다. 캠페인의 통과 조건·별점 계산을 그대로 사용한다. 결과는 `passed` / `time_limit` / `rank_cutoff`, 종료 이유는 `restart` / `navigation` / `page_exit` / `render_error`다. 연습 주행은 `track_id=practice`, 별점은 0이다. `is_retry`는 동일 레이스 화면 안에서 두 번째 이후 시도다.

프레임별 입력·충돌별 이벤트는 보내지 않고 마지막 상태를 집계한다. 일시정지·계속하기는 하나의 시도다. 결과 저장 재시도·남은 AI의 완주·결과 화면 갱신은 완료를 추가 전송하지 않는다. 완료 후 다른 화면으로 나가도 중도 종료로 세지 않는다.

브라우저 강제 종료·모바일 OS의 앱 종료에서는 마지막 이벤트 전달이 보장되지 않는다. 뒤로 가기 캐시에 보관되는 `pagehide`는 종료로 판정하지 않는다. 명시적 중도 종료율과 시작 대비 종료 이벤트의 차이를 함께 본다.

## 연결 후 검증

1. 배포에서 참여 전 Google 태그 요청이 없는지 확인하고 참여한다.
2. GA4 실시간 보고서에서 화면 이동과 경기 시작을 확인한다. Tag Assistant로 디버그 세션을 연결하면 DebugView에서 매개변수를 확인할 수 있다.
3. 일시정지 → 계속하기, 재시작, 포기, 완주, 실격을 각각 수행한다. 시작/완료 중복과 완료 이후 포기가 없는지 확인한다.
4. 참여 해제 후 전송 중단, 설치 앱 동작을 확인한다. 광고 차단을 켜도 게임·저장이 정상이어야 한다.

측정 ID와 실제 배포 전에는 자동·모의 검증만 가능하며 GA4 수신·실시간 보고서·DebugView 검증은 미완료 상태다.

로컬 자동 테스트에서 동의·전송 실패 격리·경기 이벤트 중복 방지를 검증했다. Google 태그 요청을 모의 처리한 브라우저에서도 참여 전/거절 후 태그 미로드, 참여 후 현재 화면만 전송, 일시정지·재개 시작 중복 없음, 재시작과 포기의 구분, 참여 해제 후 화면 이동 이벤트 차단을 확인했다. 모바일 390×844 화면에서 안내·상세 창의 가로 넘침이 없는 것도 확인했다. 모의 테스트는 실제 Google 수신이나 iPhone 설치 앱을 검증하지 않는다.

## 이후 판단

배포 후 2–4주 동안 방문 대비 주행 시작률, 완주·통과율, 재도전, 다음날·다음주 재방문을 본다. 기기·트랙·난이도로 나눠 이탈을 확인한다. 표본이 적으면 비율은 결론보다 관찰에 사용한다.

계속 플레이하는 이용자와 저장 백업 수요가 확인되면 선택적 로그인·클라우드 저장을 별도 단계로 만든다. 게스트 게임을 유지하고 로그인 때 로컬 진행을 계정으로 옮긴다. 인증·게임 저장은 별도 서비스가 담당한다. User-ID 연동은 로그인 도입 시 다시 설계한다.
